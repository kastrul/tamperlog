# RFC 3161 time-stamp anchor

Package `github.com/kastrul/tamperlog/anchor/rfc3161` is the shipped
`anchor.Provider`. It sends the SHA-256 of each seal to a time-stamp
authority (TSA) and stores the DER `TimeStampToken` it gets back beside the
seal. A verifier later checks the token against the seal hash and the roots
you pinned, and reports the time the authority bound to it.

```go
roots := x509.NewCertPool()
roots.AppendCertsFromPEM(skRootPEM) // see "Which roots to pin"

provider := rfc3161.NewProvider(
    rfc3161.New("https://tsa.example/tsa", rfc3161.WithTimeout(20*time.Second)),
    rfc3161.NewVerifier(roots,
        rfc3161.WithRequiredPolicies(asn1.ObjectIdentifier{0, 4, 0, 2023, 1, 1}),
        rfc3161.WithMaxAccuracy(2*time.Second),
    ),
)
```

Hand `provider` to `anchor.NewRunner`. The runner anchors every seal that
lacks a proof, and `Provider.Anchor` verifies each fresh token before it is
stored, so a TSA that answers with a token that does not chain to your roots
fails loudly at anchoring time rather than silently at audit time.

## What a token proves

A `TimeStampToken` is a CMS `SignedData` whose content is a `TSTInfo`
carrying a `messageImprint` (here the SHA-256 of the seal's canonical bytes),
a `genTime` in UTC, an optional `accuracy`, a serial number, the TSA's policy
identifier and the nonce the client sent. The TSA signs it with a certificate
that carries the `id-kp-timeStamping` extended key usage marked critical.

A verified token therefore establishes that *this exact 32-byte value existed
no later than `genTime + accuracy`*, according to the named authority. Because
the seal commits to every stream head and to the previous seal, the token
transitively bounds the time of every event sealed up to that point: an event
in seal *n* was recorded between the `genTime` of seal *n-1* and that of seal
*n*. Nobody can back-date a seal or an event without the TSA's private key.

The token proves nothing about the content of the seal (the TSA only ever sees
a hash), about who requested it, or about anything after `genTime`.

A **qualified** token, issued by a provider listed in an EU trusted list for
the time-stamping service at `genTime`, additionally enjoys the eIDAS
Art. 41(2) presumption of the accuracy of the time and the integrity of the
bound data; whoever disputes it carries the burden of proof. Establishing
that status is the job of `anchor/rfc3161/eutl`, which supplies a function
for `WithQualifiedChecker`. Without the hook `Attestation.Qualified` is always
false; the token is still a valid, verifiable RFC 3161 time-stamp.

## Obtaining access

**SK ID Solutions demo** (Estonia). `http://tsa.demo.sk.ee/tsa` is a free,
unauthenticated endpoint for development. Tokens are signed by a demo
authority ("DEMO SK TIMESTAMPING AUTHORITY ...") under policy
`0.4.0.2023.1.1` with accuracy 1 s. Demo tokens have no legal standing and the
demo chain may be rotated without notice; use them for tests only.

```sh
openssl ts -query -data file.txt -cert -sha256 \
  | curl -s -H 'Content-Type: application/timestamp-query' --data-binary @- \
      http://tsa.demo.sk.ee/tsa -o response.tsr
openssl ts -reply -in response.tsr -text
```

**SK ID Solutions production.** Qualified time-stamps are sold in monthly
plans; the public price list starts at roughly 36 EUR for 1,000 stamps a
month and falls to 0.006 EUR per stamp at 500,000 a month. Access is
contractual: see <https://timestamping.skidsolutions.eu/> and the
`SK-EID/Timestamping` GitHub wiki for the service description and the
production endpoint, which SK provides with the contract. Access is restricted
by source IP address, so note the egress addresses of every host that runs the
anchor runner.

**Others.** D-Trust (DE) and Sectigo also operate eIDAS-qualified TSAs over
RFC 3161 with contractual access; any TSA that speaks RFC 3161 over HTTP works
with this client. DigiCert runs a public non-qualified endpoint that is fine
for a second, independent anchor (see "Limitations").

The protocol is plain HTTP POST with `Content-Type:
application/timestamp-query`. Prefer an `https://` endpoint when the operator
offers one; the token itself is signed, so transport security protects
availability and privacy of the hash rather than integrity.

## Which roots to pin, and how

The verifier trusts **only** the pool you pass to `NewVerifier`. It never
consults the system pool, and a nil or empty pool rejects every token. This is
deliberate: the system pool contains hundreds of CAs, none of which should be
able to vouch for your audit trail's timeline.

Pin the TSA operator's **root** certificate, not the TSA signing certificate.
TSA signing certificates are rotated every few years; the root outlives them
and lets you verify old and new tokens with one configuration. SK publishes
its certificates at <https://www.skidsolutions.eu/en/repository/certs/>.
Download the root that issued the time-stamping chain you receive (compare
with the issuer of the certificates in a token: `openssl ts -reply -text` or
`rfc3161.ParseToken` prints them), verify its fingerprint against the one
SK publishes, and commit the PEM to your deployment configuration.

```go
roots := x509.NewCertPool()
if !roots.AppendCertsFromPEM(pem) { log.Fatal("no certificates in root PEM") }
v := rfc3161.NewVerifier(roots)
```

If the operator's chain has an intermediate that tokens do not include, add
it with `WithIntermediates`. When the root is rotated, append the new root to
the pool and keep the old one for as long as you must verify tokens signed
under it.

Do **not** build the root pool from the certificates inside a token. A token
carrying its own root proves only that it is self-consistent, which any
attacker with a laptop can arrange. The integration test offers that mode
(`TAMPERLOG_TSA_TRUST_RESPONSE=1`) for smoke-testing a new endpoint, and says
so in its output.

Pin the policy too (`WithRequiredPolicies`): SK issues qualified stamps under
`0.4.0.2023.1.1`. A token under a different policy is not what you paid for
and should not pass.

## Verification steps

`Verifier.Verify(ctx, digest, token)` performs, in order:

1. **Structure.** The token is DER with no trailing bytes: a `ContentInfo` of
   type `id-signedData`, a `SignedData` of version 1 to 5 with `eContentType`
   `id-ct-TSTInfo`, exactly one `SignerInfo` with signed attributes, and a
   `TSTInfo` of version 1 with no critical extensions. Included
   certificates must parse; attribute certificates are rejected.
2. **Imprint.** The `messageImprint` algorithm is SHA-256 (parameters absent
   or NULL) and the hashed message equals `digest`.
3. **Signer certificate.** The certificate the `SignerIdentifier` names
   (issuer and serial, or subject key identifier) is among the included
   certificates. Two different matching certificates is an error.
4. **Signature.** The `SignerInfo` digest algorithm is SHA-256, -384 or -512
   and is listed in `SignedData.digestAlgorithms`; the signature algorithm is
   RSA PKCS#1 v1.5 (`rsaEncryption` or `shaNNNWithRSAEncryption`), RSASSA-PSS
   with explicit parameters, or ECDSA with SHA-2, and agrees with the digest
   algorithm and the key type; RSA keys are at least 2048 bits. The signature
   is verified over the signed attributes re-encoded as `SET OF`.
5. **Signed attributes.** `content-type` equals `id-ct-TSTInfo`;
   `message-digest` equals the digest of the `TSTInfo` DER under the signer's
   digest algorithm; `signing-certificate` (ESSCertID, SHA-1) or
   `signing-certificate-v2` (ESSCertIDv2, SHA-256 by default) is present and
   its first entry hashes to the signer certificate, with issuer and serial
   checked when given. Duplicate attributes and multi-valued attributes are
   rejected.
6. **Chain.** The signer chains to your roots with `CurrentTime = genTime`
   and the `timeStamping` key purpose, using your intermediates and the
   other certificates in the token.
7. **Extended key usage.** The signer certificate's EKU extension is present,
   marked critical and lists `id-kp-timeStamping` (Go's chain verification
   checks presence, not criticality).
8. **Policy and accuracy.** The policy is one of `WithRequiredPolicies` (if
   set) and the accuracy is within `WithMaxAccuracy` (if set).
9. **Qualified status.** The `WithQualifiedChecker` hook, if set, is called
   with the signer certificate and `genTime`; an error fails verification.

Every failure wraps `anchor.ErrInvalidProof`. The result is an
`anchor.Attestation` with `Time = genTime`, `Accuracy`, `Authority` (signer
subject), `Qualified` and `Details` (`policy`, `serial`, `signer_sha256` and
`tsa` when the token names one).

The client performs its own checks on a fresh response before the verifier
runs: HTTP 200, `Content-Type: application/timestamp-reply` (a missing header
is tolerated), body at most 1 MiB, status `granted` or `grantedWithMods`
(anything else is a `*StatusError` with the `failInfo` bits and status text),
and that the token's imprint and nonce echo the request. The nonce is a fresh
64-bit random value per request, so a replayed token is rejected.

`ParseToken` exposes the parsed fields (parsed, **not** verified) for tooling.

## Cost

One token per seal. With the default hourly seal interval that is
24 x 30 = **720 stamps a month**, inside SK's smallest plan (1,000 stamps,
about 36 EUR a month, about 0.05 EUR per seal at that volume). Sealing every
5 minutes is 8,640 a month (the 10,000 plan, about 190 EUR); every minute is
43,200 (the 100,000 plan, about 1,000 EUR). Per-event stamping is never
sensible: 2 million events a month would cost about 12,000 EUR at the cheapest
tier and would prove nothing the seal chain does not. The seal interval, not
the event rate, sets the bill; choose it from the time resolution you need to
attest, since an event's time is only bounded to the interval between the
seals around it.

The demo endpoint is free. Running a second, independent TSA roughly doubles
the figure.

## Limitations

- **TSA key compromise.** If the TSA's signing key leaks, the operator revokes
  the certificate with reason `keyCompromise` and every token signed with it
  loses its standing, including genuine ones, because a forged token with a
  back-dated `genTime` is indistinguishable from a real one. RFC 3161
  section 4 therefore recommends obtaining tokens from **two different TSAs**
  for anything that must survive the compromise of one. The `anchor` package
  accepts several providers; a second RFC 3161 provider with another operator,
  or a different kind of anchor altogether, closes this gap. Note that this
  verifier does not check revocation at all; it verifies validity at
  `genTime`, which is what matters for an old token, and leaves "was the key
  compromised later" to operational monitoring of the operator's CRL.
- **Certificate expiry and algorithm ageing.** A token stays verifiable for as
  long as you keep the roots and the token, but its evidential value rests on
  the signature algorithm staying unbroken and the certificate having been
  valid at `genTime`. RFC 3161 section 4 advises **re-time-stamping** before
  the TSA certificate expires or the algorithm weakens: time-stamp a hash
  over the old token (or over a seal that commits to it, which the seal chain
  does by construction, since each seal commits to the previous one and the
  runner anchors every seal). Keep anchoring new seals and the chain renews
  itself; what you must not do is stop.
- **Accuracy is about the seal, not the event.** A 1 s accuracy on a seal
  bounds every event in it only to the interval between that seal and the
  previous one.
- **Availability.** A TSA outage leaves seals unanchored until the runner's
  grace period passes and an `anchor.failed` event is recorded (ADR 0009).
  Seals and events are never delayed by anchoring.
- **Hash linkage.** Identical digests sent to a TSA are linkable by the
  operator. Seal hashes are unique by construction, so this does not apply
  here, but do not send the same digest twice on purpose.
- **Qualified status is a separate check.** A token from SK's production TSA
  is qualified only if SK was listed for that service at `genTime`; this
  package cannot know that without the trusted list, which `eutl` supplies.

## Verified end to end (2026-10-17)

The CLI anchored and verified a seal against the SK ID Solutions demo
endpoint with this root, downloaded from the SK certificate repository
(https://www.skidsolutions.eu/resources/certificates/, tab "TSA certificates"):

| Environment | Root to pin | Source |
|---|---|---|
| demo (`http://tsa.demo.sk.ee/tsa`) | `CN=TEST of SK TSA CA 2023E` (issuer `TEST of SK ID Solutions ROOT G1E`, valid to 2038-03-27) | `https://www.skidsolutions.eu/upload/files/TEST_of_SK_TSA_CA_2023E.der.crt` |
| production | `SK TSA CA 2023E` or `SK TSA CA 2023R` | `https://c.sk.ee/SK_TSA_CA_2023E.pem.crt`, `https://c.sk.ee/SK_TSA_CA_2023R.pem.crt` |

Convert DER to PEM with `openssl x509 -inform der -in x.der.crt -out x.pem`
and pass the PEM file to `--tsa-roots` (several certificates in one file are
fine). The demo token carried policy `0.4.0.2023.1.1`, accuracy 1 s, an ECDSA
signer `DEMO SK TIMESTAMPING UNIT 2025E`, and only the signer certificate in
its chain, which is why pinning the issuing CA is required. Check the
fingerprint of any downloaded root against SK's published values before
trusting it in production.
